パスワード保管庫の AWS 構成案

使った分だけ課金されるサービスだけで組む案（2026年11月時点の検討メモ）

結論

待機中の固定費をほぼゼロにするため、月額の固定料金がかからないサービスだけで構成します。止まっている間に残る費用は、保管しているファイルの保管料（数MB分）程度です。

暗号化と復号は利用者の端末（ブラウザ）の中だけで行い、AWS には暗号化済みのファイルだけを置きます。AWS 側の設定ミスや侵入があっても、マスターパスワードがなければ中身は読めません。

使う AWS サービスは6つです。入口をまとめる CloudFront（コンテンツ配信サービス）、画面と保管庫のファイルを置く S3（ファイル保管サービス）を2つ、ログインを担う Cognito（認証サービス）、API の受付とログイン確認をする API Gateway（API の受付サービス）、保管庫の読み書きを仲介する Lambda（呼ばれたときだけ動くプログラム実行環境）です。

構成図

緑の枠は、暗号化前の情報（平文）を扱ってよい範囲です。青い点線の枠は AWS で、ここには暗号文しか入りません。図の中の丸数字は、後の「処理の流れ」の手順番号を表します。点線の矢印は、データではなく確認のための参照を表します。

処理の流れ

保管庫は、KeePass 系ソフトで使われる暗号化データベース形式（kdbx 形式）のファイル1つとして扱います。暗号化の形式を自分で決めずに済み、いざとなればファイルを KeePassXC（OSS のパスワード管理ソフト）で直接開けるためです。

  1. 画面を取得する。ブラウザが CloudFront 経由で、画面配信用の S3 から HTML と JavaScript を受け取ります。
  2. ログインする。Cognito にログインし、アクセストークン（ログイン済みであることを示す、期限付きの電子署名付きデータ）を受け取ります。ここで使うパスワードは、保管庫を開くマスターパスワードとは別のものにします。
  3. 保管庫を取得する。アクセストークンを付けて /api/ に要求すると、API Gateway がトークンを検証し、Lambda が保管庫用の S3 から暗号化済みファイルを返します。あわせて、ファイルの版を表す識別子（ETag）も返します。
  4. 端末の中で復号・編集・再暗号化する。マスターパスワードで復号し、編集後に再び暗号化します。この間、平文は端末の外に出ません。
  5. 保存する。手順3で受け取った ETag を付けて送ります。Lambda は「S3 上のファイルがその版のままなら上書きする」という条件付き書き込みを行います。別の端末が先に保存していた場合は失敗するので、画面は最新版を取り直して変更を取り込んでから保存し直します。

各サービスの役割と設定のポイント

サービス役割料金が発生する条件設定のポイント
CloudFront画面と API の入口を1つのドメインにまとめる転送量とリクエスト数に応じて（少人数なら常時無料枠に収まる見込み）既定で付く xxxx.cloudfront.net のドメインを使えば、ドメイン代も証明書代もかからない。レスポンスヘッダーポリシー（返答に付けるヘッダーの設定）で CSP（読み込んでよいスクリプトを制限する仕組み）を厳しく設定する。/api/ 以下はキャッシュを無効にし、Authorization ヘッダーを転送する。
S3（画面配信用）画面の HTML・JavaScript を置く保管容量とリクエスト数に応じて公開設定はせず、OAC（Origin Access Control。CloudFront からの読み取りだけを許可する仕組み）で CloudFront 経由に限定する。
Cognito利用者のログインとアクセストークンの発行月間の利用者数に応じて（少人数なら無料枠内の見込み）自己登録を無効にし、管理者が利用者を作成する。多要素認証（パスワードに加えて認証アプリのコードも求める方式）を必須にする。
API GatewayAPI の受付とトークン検証リクエスト数に応じて（100万件あたり1ドル程度）HTTP API 型の JWT オーソライザー（トークンの署名と有効期限を自動で確認する機能）で Cognito のトークンを検証する。利用者数に見合った流量制限をかける。
Lambda保管庫ファイルの取得と条件付き保存呼び出し回数と実行時間に応じて保存先のパスは、トークンに含まれる利用者 ID から Lambda 側で組み立てる（例 vaults/{利用者ID}/vault.kdbx）。画面から送られたパスは使わないので、他人の保管庫には触れない。VPC（AWS 内の閉じたネットワーク）には入れない。入れると外部通信に NAT ゲートウェイ（月額固定の通信中継）が必要になるため。リクエストやファイルの中身はログに出さない。
S3（保管庫）暗号化済み kdbx ファイルの保管保管容量とリクエスト数に応じて（数MBならほぼ0円）パブリックアクセスを全面ブロックする。バージョニング（上書き前の版を残す機能）を有効にし、ライフサイクルルール（古い版を自動削除する設定）で古い版を一定期間後に消す。サーバー側暗号化は無料の SSE-S3 で足りる。
運用ログ、費用の監視、操作履歴ログの保管量に応じてCloudWatch Logs は保持期間を短く設定する。AWS Budgets で月1ドルなど低い金額に通知を設定し、想定外の課金にすぐ気付けるようにする。CloudTrail は既定のイベント履歴（直近90日分の操作履歴）で足りるので、証跡（履歴を S3 に保存し続ける設定）は作らない。

採用しなかったサービスと理由

いずれも待機中に固定費がかかるか、この規模では不要なものです。必要になったら後から足せます。

DynamoDB（従量課金のデータベース）

保管庫がファイル1つなら、版の管理は S3 の条件付き書き込みで足ります。人ごとに見せる項目を分ける共有機能や、操作履歴を作るときに追加を検討します。

KMS のカスタマー管理キー（自分で管理する暗号鍵）

鍵1つあたり月額がかかります。中身は端末で暗号化済みなので、S3 側の暗号化は無料の SSE-S3 で十分です。

AWS WAF（Web アクセスの防御サービス）

設定1つあたり月額がかかります。代わりに API Gateway の流量制限と Cognito の多要素認証で守ります。

Route 53（DNS サービス）と独自ドメイン

ホストゾーン（ドメインの設定を置く場所）に月額がかかります。CloudFront 既定のドメインで HTTPS が使えるので、独自ドメインが必要になるまでは使いません。

確認が必要な点

この構成案は、各サービスの仕様を実機で確かめる前の案です。着手前に次の点を確認してください。

保管庫のファイルサイズの上限。Lambda が受け取れるリクエストの大きさには6MBの上限があります。秘密鍵ファイルを添付しても通常は収まりますが、大きなファイルを入れる場合は、Lambda が発行する署名付き URL（期限付きで S3 に直接アクセスできる URL）を使う方式への変更が必要です。

S3 の条件付き書き込みの動作。ETag を指定した上書き（If-Match 指定）が、使う SDK のバージョンとバージョニング有効のバケットで期待どおりに失敗・成功するか、実機で確認します。

kdbxweb の Argon2 対応。kdbxweb は Argon2（kdbx 形式の新しい版で使う鍵導出方式）の計算処理を自前で持たず、外部の実装を組み込む作りです。どの実装を組み込むかと、そのライブラリの保守状況を確認します。

無料枠の扱い。2025年7月以降に作成したアカウントは、無料枠がクレジット方式に変わっています。各サービスの常時無料枠が自分のアカウントでどう適用されるかは、請求コンソールで確認します。
